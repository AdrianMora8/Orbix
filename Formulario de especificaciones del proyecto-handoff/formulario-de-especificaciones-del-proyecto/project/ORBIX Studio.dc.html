Arquitectura hexagonal en proyectos académicos

Martina Ríos
Backend Lead · ORBIX Studio

Cuando arrancamos un proyecto en la universidad, la tentación es escribir todo el código pegado al framework y a la base de datos. Funciona para la demo, pero se vuelve imposible de mantener apenas cambia un requisito. La arquitectura hexagonal nos dio una forma clara de separar la lógica de negocio de los detalles de infraestructura.

El núcleo no conoce el mundo exterior

La idea central es que el dominio se comunica con el exterior a través de puertos (interfaces), y los adaptadores implementan esos puertos. Así, la base de datos, la API HTTP o la cola de mensajes son intercambiables sin tocar la lógica de negocio.

diagrama · puertos y adaptadores

En la práctica esto significó definir primero los casos de uso, escribir los tests contra ellos, y recién después decidir qué motor de base de datos usar. El equipo pudo trabajar en paralelo sin bloquearse.

"Si tu lógica de negocio depende de tu ORM, no tenés arquitectura: tenés un CRUD con más pasos."

Qué nos llevamos

No todo proyecto necesita este nivel de separación, y aplicarlo sin criterio agrega complejidad. Pero entender el patrón nos hizo mejores tomando decisiones sobre dónde poner cada cosa.
